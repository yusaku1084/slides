# 想定問答集（Q&A対策）

LT後の質問タイム用。ビギナー→実運用→シニアの順。
数字を断定してよいのはpnpm実測（22.3秒 / 12.6秒 / ダウンロード0）のみ。マージ運用・ディスク使用量は未検証と正直に答える。

## ビギナー向け

**Q. worktreeは何個まで作れる？**
上限なし。ただし机が増えるほど人間の管理コストが増えるので、自分が同時に面倒を見られる数（2〜4個）から始めるのがおすすめ。

**Q. worktreeを消すとブランチも消える？**
消えない。`git worktree remove` は作業ディレクトリを片付けるだけ。ブランチ本体は `git branch -d` で別途削除する。

**Q. worktreeはどう消すのが正しい？**
`git worktree remove <path>` で消す。フォルダを `rm -rf` で消すと管理情報の残骸が残るので非推奨（残ってしまったら `git worktree prune` で掃除）。

**Q. `fatal: 'task-a' is already checked out` と出た。壊れた？**
仕様。同じブランチは2箇所で同時にcheckoutできない（LT中に話した安全装置）。どのworktreeが使っているかは `git worktree list` で分かる。

**Q. worktree側の `.git` がフォルダじゃなくてファイルだった。大丈夫？**
正常。worktreeの `.git` は本体の `.git` への参照を書いた小さなテキストファイル。履歴の実体は本体側にしかない。

**Q. エディタはどう開くのがいい？**
worktreeごとに別ウィンドウ。「1ウィンドウ = 1机 = 1エージェント」にすると、今どこにいるか迷子になりにくい。

**Q. worktreeからも普通にpull/pushできる？**
できる。リモート設定は共有で、fetchはどこで実行しても全worktreeに反映される。

## 実運用の質問

**Q. 実際、複数のエージェントはどうやって起動してる？ターミナル構成は？**
原則「**1worktree = 1ターミナル**（ペイン/タブ/ウィンドウ）」。自分はエディタのウィンドウをworktreeごとに開き、それぞれの統合ターミナルでエージェントを起動した。tmux派なら、worktree（机）ごとにウィンドウを作っておく:

```bash
for w in a b c; do
  tmux new-window -n "myapp-$w" -c "../myapp-$w"
done
```

**Q. worktreeはタスクごとに作り直す？使い回す？**
流派が2つある。**作り直す派**はブランチ名 = ディレクトリ名にできて分かりやすいが、毎回セットアップが走る。**常設で使い回す派**（自分はこっち）は机を数個並べておき、タスクごとに中で `git switch -c` する。作る手間ゼロで速い代わりに、**前タスクの残骸**（ビルド成果物・依存）が残るのが弱点。切り替え時のclean/installを怠ると、まさにvendor事故と同じ「古い残骸」問題を踏む。

**Q. ペインが並ぶと、今どの机にいるか迷子にならない？**
なる。机を使い回す運用だとディレクトリ名がタスクを表さないので、**プロンプトにブランチ名を表示**しておく（starship等）＋迷ったら `git worktree list`（机⇔ブランチの対応が一覧で出る）。

**Q. コミットやstashはworktree間で混ざらない？**
コミットはブランチ単位なので混ざらない。stashは置き場が共有なので、worktreeをまたいで適用できる（便利だが、意図しないworktreeでpopしないよう注意）。

**Q. `.env` や証明書を毎回用意するのが面倒**
worktree作成スクリプトの中でコピー（またはシンボリックリンク）するのが定石。ただしDBデータのような「共有すべき実体」はリンクせず、そもそもworktreeから触らない。

**Q. ポート衝突の具体的な対処は？**
dev serverのポートをworktreeごとに環境変数でずらす。strictPort系の設定だと自動で隣のポートに逃げてくれないので、明示的に指定する。

**Q. installが毎回走るのは遅くない？**
pnpmなら2個目以降は速い。実測で1個目22.3秒 → 2個目以降12.6秒、ネットからのダウンロードは0（グローバルストアからのハードリンク再リンクのみ）。npm/yarnは実ファイルコピーになるのでここまで速くならない。

**Q. マージやコンフリクトの運用はどうしてる？**
今回検証したのは環境構築まで。各ブランチをpush→PRでレビューする方針だけ決めてあり、実タスクを流したマージ運用の知見はまだ無い。次回のLTで報告予定。

## シニア向け・深掘り

**Q. 人間が複数エージェントを手動で並べる方式にした理由は？オーケストレーター型（1つのエージェントに監督させる）でもよくない？**
今回はタスクが互いに独立していて、かつマージ判断を人間が握りたかったので、人間がディスパッチャになる方式を選んだ。タスク間に依存があったり数が多い場合は、オーケストレーター型が候補になる。使い分けの話。

**Q. opcacheの件を詳しく**
vendorが別ブランチ（フレームワーク新版の検証）の名残でコードと不整合だったが、7週間起動しっぱなしのコンテナのopcacheが古いバイトコードを返し続けて不整合を隠蔽していた。再起動で初めて露呈。「再起動したら壊れた」は、実際には「ずっと壊れていたのが再起動で見えた」だった。

**Q. どうしてもworktree側でDockerを使いたい場合は？**
できる。composeのproject nameとポートをworktreeごとに分け、**DBやRedisなどステートフルな層は1組を共有**、DBは**論理DB（`app_wt1`…）で分離**する。複製するのは軽いappコンテナだけなので、「二重持ち」を避けたまま並列動作確認まで到達できる（tracked変更ゼロで組める）。今回のLTは「まずメインに一本化」までの話で、**この並列Docker検証は次回LTで報告予定**。

**Q. Jujutsu（jj）のworkspaceとの違いは？**（前回のjj LTを聞いた人向け）
発想はほぼ同じで、jj workspaceはブランチ名なし（匿名）で机を増やせる分さらに気軽。今回は「チームへの影響ゼロのgit標準機能」から始めたかったのでworktreeを選んだ。併用も可能。

**Q. bare repo + 全部worktree構成にはしない？**
メインを既存クローンのまま使う方が導入コストゼロだったのでこの形。長期運用するならbare化してメインも1つのworktreeにする流派もある。

**Q. エージェントの認証やnodeバージョンはworktreeごとに設定が要る？**
不要だった。認証はKeychain＋グローバル設定が全ペインで共有される。nodeは `.node-version` がgit管理下にあるので、全worktreeで自動的に同一バージョンに解決された。

**Q. ディスク使用量は？**
未計測。`.git` 共有のぶんcloneより軽いのは確実だが、`node_modules` や `vendor` はworktreeごとに持つ（pnpmはハードリンクなので実体は増えにくい）。次回計測する。
